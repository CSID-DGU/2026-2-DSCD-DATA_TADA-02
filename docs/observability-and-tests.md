# 서버 측정, LLM 비교와 테스트

- 범위: 서버 자체의 동작 시험과 LLM 모델 교체 비교를 분리한다.
- 현재 구현: 구조화 로그, 단계별 시간, HTTP 지표, 기능 테스트, 로컬 부하 스크립트.
- 향후 연결: Langfuse, OpenTelemetry export, Cloud Monitoring, 실제 모델 평가 데이터셋.

## 도구 선택

Langfuse를 우선 후보로 둔다. 같은 데이터셋으로 모델/프롬프트를 바꾼 실험 결과와 점수를 비교하고, LLM 호출의 시간/토큰/비용을 기록할 수 있기 때문이다. 이것은 프로젝트 요구에 따른 선택이며 모든 상황에서 최고라는 뜻은 아니다. [Langfuse 데이터셋 실험](https://langfuse.com/docs/evaluation/get-started/offline), [토큰과 비용](https://langfuse.com/docs/observability/features/token-and-cost-tracking)

LangSmith도 같은 데이터셋의 실험 비교와 여러 방식의 평가를 지원하는 대안이다. 어느 도구를 쓰더라도 평가 기준과 데이터셋은 프로젝트에서 정의해야 한다. [LangSmith 평가 유형](https://docs.langchain.com/langsmith/evaluation-types)

서버 전반의 요청 추적, 지표와 로그에는 OpenTelemetry와 배포 플랫폼의 모니터링을 사용한다. 현재의 `telemetry.span`과 `event`가 향후 SDK를 연결할 경계다. 지금 코드가 이미 OpenTelemetry 또는 Langfuse로 데이터를 전송하는 것은 아니다. [OpenTelemetry 설명](https://opentelemetry.io/docs/concepts/observability-primer/)

## 인풋: 측정 조건

- 서버 시험: 코드 버전, 데이터 버전, DB 종류, 서버 자원, 동시 요청 수, 요청 경로 구성과 반복 횟수.
- LLM 시험: 위 조건에 provider, 정확한 모델명/스냅샷, 프롬프트 버전, 출력 길이 한도, 생성 설정, timeout과 retry 정책을 추가한다.
- 평가 자료: 비교/상세 페이지별 고정 입력과 근거, 기대하는 설명 요소, 금지하는 오해, 평가 기준.
- 실행 구분: 실제 모델 호출, 모의 provider, 캐시 적중과 미적중을 각각 표기한다.

## 아웃풋: 측정할 값

| 측정 | 시작 → 끝 | 결과와 의미 |
| --- | --- | --- |
| API 앱 시간 | 서버가 요청을 받은 뒤 → 응답 객체 준비 | Server-Timing, middleware 로그. 단위 ms, 낮을수록 빠름 |
| 전체 API 왕복 | 시험 클라이언트 요청 → 본문 수신 | 네트워크/전송 포함, p50/p95/p99 |
| DB와 분석 | 분석 서비스 호출 → 스냅샷 조회/계산 완료 | 현재 analysis/evidence span. 향후 SQL 세부 span 추가 |
| LLM 생성 | provider 호출 직전 → 구조화 응답 완료 | 모델 호출 시간, 입력/출력 토큰, 오류. 스트리밍 전에는 TTFT 없음 |
| 결과 검증 | LLM 결과 수신 → 형식/근거 ID 검사 완료 | 검증 지연과 실패 비율 |
| 차트 표시 준비 | 프론트 조회 시작 → 상태 반영 후 animation frame | Performance `ui:charts-ready`, 차트 애니메이션 전체 완료 시간은 아님 |
| 해설 준비 | 프론트 해설 요청 시작 → 최종 상태 수신 | `ui:commentary-ready`, 캐시/미적중 분리 |
| 처리량 | 시험 시작 → 모든 요청 완료 | 완료 요청 수 ÷ 초, requests/s |
| 오류율 | 전체 시험 동안 | 비2xx/전송 실패 수 ÷ 전체 요청 수 |
| 가용성 | 정해진 관측 기간 | 외부 probe 성공 수 ÷ 전체 probe 수. 현재 미구현 |
| 자원 | 관측 기간 | CPU, 메모리, DB 연결 수. 현재 로컬 스크립트는 미수집, Cloud Monitoring 후속 |

`p50`은 요청 절반이 이 시간 안에 끝났다는 뜻이다. `p95`는 95%가 이 시간 안에 끝났다는 뜻이며, 일부 느린 요청을 평균보다 잘 드러낸다. 병렬 처리 단계의 시간은 겹칠 수 있으므로 전체 시간에 단순 합산하지 않는다.

## 서버 기능 테스트

| 시험 | 확인할 동작 |
| --- | --- |
| 기본 조회 | 위치 목록과 필터, 비교 최대 5개, 상세 이력, 준비/생존 응답 |
| 입력 | 0개/6개/중복 후보, 지원하지 않는 업종, 분기 형식, 반경 |
| 계산 | 평균 매출, 평균 거래, 평균 결제금액, YoY의 독립적인 산술 대조 |
| 결측 | 자료 없는 상권을 null로 보존, 분모 0 처리 |
| 지도 자료 | 기준 매물 소유 상권 확인, 반경 필터와 거리 정렬 |
| 실패 | 내부 예외는 500, DB 준비 실패는 503, 기본 생존 응답 유지 |
| LLM 경계 | 모의 provider 성공/오류/timeout/잘못된 근거 ID |
| 캐시 | 후보 순서 변경 재사용, 페이지/모델 변경 무효화 |
| 중복 생성 | 같은 DB를 쓰는 두 서비스 인스턴스의 요청 경합 |
| 접근 | 토큰이 설정된 해설과 metrics의 인증 확인 |
| UI 규칙 | 여섯 번째 후보 차단, 제거 후 대체, 화살표로 모든 후보 접근 |

현재 LLM 테스트는 실제 공급자와 통신하지 않는 모의 시험이다. 유료 호출 품질과 실제 모델 지연을 검증했다는 뜻은 아니다.

## 로컬 부하 시험

`scripts/load_test.py`는 localhost에서만 동작한다. `/areas?q=성수`, `/areas/3120052/analysis`, `/health/ready`를 번갈아 읽는다. 준비 요청을 따로 수행하고 측정한다. 서버 상태를 변경하거나 LLM을 호출하지 않는다.

- 소규모: 200회, 동시 1개와 10개를 각각 실행한다.
- 이후 확장: 3개 비교 POST 혼합, 큰 목록 응답, 장시간 soak, DB 장애 복구, LLM 지연 중 일반 조회 등을 별도 시나리오로 추가한다.
- 배포 시험: Cloud Run 콜드 스타트와 warm 요청을 나누고, DB 연결 풀과 인스턴스 수를 함께 기록한다.
- 합격 기준: 실제 배포 환경과 사용자 대기 목표를 확인한 뒤 정한다. 로컬 수치만 보고 임의 SLO를 달성했다고 선언하지 않는다.

결과 파일의 모든 요청이 2xx여도 장기 안정성, 실제 데이터의 처리 용량, Cloud SQL/Cloud Run 운영 성능까지 검증한 것은 아니다.

## 모델별 품질 비교

처음에는 예를 들어 30~50개의 대표 사례로 시작할 수 있다. 이 개수는 설계 제안이며 평가 완료 사실이 아니다.

| 품질 기준 | 확인 방법 |
| --- | --- |
| 숫자와 단위 | 인용한 값이 입력 근거와 맞는지 자동 검사 후 표본 검토 |
| 근거 일치 | 각 문장이 제공한 근거에서 도출되는지 사람/심사 모델 평가 |
| 유형 해석 | 총매출과 점포 수, 평균 매출의 차이를 올바르게 설명하는지 |
| 예측 구분 | 미래를 확정하거나 신규점 매출로 설명하지 않는지 |
| 수요 해석 | 거래를 고객 수로, 유동인구를 구매자 수로 바꾸지 않는지 |
| 임대와 메뉴 | 광고 원조건, 미확보, 확인일과 범위를 지키는지 |
| 이해도 | 용어와 비교 기준을 독자가 이해할 수 있게 연결하는지 |
| 유용성 | 숫자를 반복하는 데 그치지 않고 페이지 질문에 답하는지 |

같은 입력 데이터와 프롬프트를 유지하고 모델만 바꾸는 시험을 먼저 한다. 그다음 프롬프트까지 조정한 시스템 비교를 별도 실험으로 둔다. 이 두 실험을 섞으면 어떤 변경이 품질 차이를 만들었는지 알기 어렵다.

캐시 미적중이 필요한 모델 비교는 평가용 별도 DB나 캐시를 거치지 않는 harness로 실행한다. 운영 API에 누구나 쓸 수 있는 `bypass_cache`를 노출하지 않는다. 모델별 반복 실행, 출력 순서 무작위화, 평가자에게 모델명을 숨긴 비교를 사용한다. 실패와 거부도 결과에서 제외하지 않는다.

LLM 심사 점수는 정답이 아니다. 숫자 검증과 사람 평가를 기준으로 심사자의 일관성과 편향을 확인한다. 여러 품질/지연 지표를 한 점수로 무리하게 합치기보다 품질, p95 지연과 비용을 함께 비교한다.

## 나중에 기록할 실험 행

`experiment_id`, `case_id`, `provider`, `model`, `prompt_version`, `data_version`, `metric_version`, `cache_hit`, `concurrency`, `llm_ms`, `api_ms`, `input_tokens`, `output_tokens`, `cost_source`, `cost`, `status`, `numeric_score`, `grounding_score`, `human_score`.

가격은 시점과 계약에 따라 달라지므로 자동 추정 가격과 공급자 청구/정산값을 구분한다. 로그에 전체 사용자 입력과 비밀 값을 무조건 보내지 않는다.
